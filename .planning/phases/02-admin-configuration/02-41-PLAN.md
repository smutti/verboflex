## CR-12 split rationale

Questo piano è il confine API/generated-client tra l'autorità persistente di 02-40 e la UI/E2E di 02-42. Tenerlo separato conserva nello stesso ciclo RED→GREEN il contratto OpenAPI e la rigenerazione deterministica, evita ownership concorrente dei file backend/frontend generati e fornisce a 02-42 simboli reali già verificati.

## File-count exception

I dieci file restano in un solo piano perché formano un'unica autorità API→OpenAPI→client: Task 1 modifica esattamente cinque file di route/schema/test, mentre i cinque file di Task 2 sono il contratto OpenAPI, due artefatti client generati atomicamente e i relativi test di drift. Separarli permetterebbe di committare un contratto backend senza il client canonico sincronizzato o di rigenerare da un contratto non ancora verificato; nessun task supera cinque file.
