# Phase 3 — UI Design Contract

> Visual and interaction contract for import-grade Bitbucket status, recovery, and rewritten-baseline reconciliation. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope and Provenance

Phase 3 extends the existing administrator control plane in exactly three places:

- The Bitbucket page reports the expanded read/write and pull-request capability profile required by the locked organizational connection, while making clear that imports remain read-only and provider mutations are not executed in this phase.
- The product Mappings page exposes one compact operational status and one manual import control per server-projected published mapping.
- The product Overview page shows a local count of mappings that may be stale after a failed refresh; no workspace-wide or administration-wide banner is added.

The rewritten-history flow is a mapping-scoped confirmation surface opened from the normal mapping action area. It shows the old and proposed commits and the complete bounded localization-file delta before one atomic mapping-level confirmation.

This contract preserves all Phase 3 decisions D-01 through D-18 in `03-CONTEXT.md`, requirements BITB-02, BITB-05, and BITB-06, the existing approved Phase 2 visual contract, and the current frontend implementation. Canonical translation parsing, searchable imported strings, edit reconciliation, source writes, commits, pull requests, automatic import schedules, automatic retry, and full attempt history are outside this phase.

### Product language

All visible copy remains English, matching the existing application. Provider bodies, raw source content, OAuth scope strings, tokens, secrets, stack traces, and unsanitized diagnostics must never be rendered. Branches, paths, repository identities, and commit hashes are data, never trusted markup.

## Information Architecture

| Screen / Surface | Route | Phase 3 purpose | Primary elements |
|------------------|-------|-----------------|------------------|
| Bitbucket Connection | `/admin/bitbucket` | Report whether the organizational connection has the import and future PR capability profile. | Existing connection status, capability profile, bounded timestamps, connect/reconnect/revoke actions. |
| Product Overview | `/admin/products/:productId/overview` | Summarize mapping freshness locally. | Existing lifecycle state plus an affected-mapping count when one or more mappings may be stale. |
| Product Mappings | `/admin/products/:productId/mappings` | Operate and inspect imports without mixing them into draft editing. | `Published mapping imports` section, mapping status rows/cards, last baseline, latest execution, manual action. |
| Rewritten Baseline Review | Dialog opened from one mapping row | Compare current and proposed source identity, inspect localization-file changes, and confirm the mapping atomically. | Repository-side summaries, old/new commits, added/modified/removed files, cancel and confirm actions. |

### Navigation and authority

- Keep the existing product subnavigation exactly `Overview`, `Repositories`, `Mappings`, `Preview`; do not add an Imports destination.
- On the Mappings route, place `Published mapping imports` before the existing draft mapping list and edit form. Draft configuration remains visually and semantically separate.
- Import actions target published mappings only. Candidate-only mappings remain edit/preview/publish concerns and never gain import authority from being visible in the browser.
- Render controls only from the backend's generated, server-authorized mapping projection. A client role check, route parameter, cached success, or prior capability result never grants import or reconciliation authority.
- Preserve server order for mapping rows and file deltas. Do not client-sort provider identities or merge active and candidate mappings.

## Visual and Layout Contract

### Focal hierarchy

1. Existing page title and page-level lifecycle or connection state.
2. Mapping import state, especially `May be stale` or `Review required`.
3. Last successful baseline and latest execution metadata.
4. Manual action and sanitized recovery guidance.

### Layout rules

- Preserve the existing full-width authenticated shell and `32px` page-section gap. Do not add a dashboard-card grid or global alert banner.
- Use the existing page gutters: `24px` below `768px`, `32px` from `768px` upward.
- The Bitbucket page stays within `max-w-3xl`; its capability profile is a flat bordered Secondary section below the existing connection status, never a nested card.
- The Mappings page remains full-width. At `>=768px`, `Published mapping imports` uses a semantic table with columns `Mapping`, `Import status`, `Last successful baseline`, `Latest execution`, and `Actions`.
- Below `768px`, the same fields render as border-separated stacked articles in the same accessible order. Actions are full-width when needed and never cause page-level horizontal scrolling at `320px`.
- The Product Overview affected count sits directly below lifecycle actions and before revision tabs. It is compact text plus Badge, not an Alert or dismissible banner.
- Rewritten-baseline review uses an Alert Dialog no wider than `768px`, with a keyboard-scrollable content region capped at `80vh`. At narrow widths, commit pairs and file-delta rows stack vertically.
- Do not nest mapping status cards. One border per row/article and one border around a section is the maximum hierarchy.

### Status presentation

Every state has readable text and, where useful, a Lucide icon; color is supplementary.

| State | Visible label | Tone | Meaning |
|-------|---------------|------|---------|
| No logical import exists | `Not imported` | Neutral outline | No successful baseline and no active execution. |
| Job accepted | `Queued` | Neutral outline | Durable work exists but has not begun. |
| Worker executing | `Running` | Neutral outline | Current execution is in progress; no percentage is shown. |
| Latest execution accepted | `Current` | Success green | Latest source resolution completed and the resulting baseline is active. |
| Refresh failed, baseline retained | `May be stale` | Warning amber | The last successful baseline remains usable, but the latest refresh failed. |
| Rewritten history detected | `Review required` | Warning amber | Proposed baseline is readable but cannot replace the current baseline without confirmation. |
| Failure with no successful baseline | `Import failed` | Destructive red | The mapping has no usable import baseline. |

- `May be stale` must not use destructive red because a usable last baseline remains active.
- `Import failed` is red only when no successful baseline exists.
- `Queued` and `Running` retain the previously displayed successful baseline; pending work never blanks it.
- Capability rows use `Ready`, `Reauthorization required`, or `Unavailable` exactly as projected by the generated API. Do not parse or render raw OAuth scope text.

## Interaction Contracts

### Bitbucket capability profile

- Replace the obsolete visible label `Read-only repository access` with `Repository and pull-request access` only after the generated backend status confirms the Phase 3 capability contract.
- Below connection status, render a `Capability profile` definition list with these exact user-facing rows:
  - `Read localization sources` — `Ready` when imports may resolve and read sources.
  - `Create branches and source commits` — `Ready for a later phase` when granted; supporting copy: `Not used during imports.`
  - `Open pull requests` — `Ready for a later phase` when granted; supporting copy: `Not used during imports.`
- A connection carrying the superseded Phase 2 read-only authority renders `Reauthorization required`; `Reconnect Bitbucket` is the existing page-level primary recovery action.
- The browser consumes closed capability fields from the generated client. It never derives readiness from scope strings, connection timestamps, or prior success.
- Connect/reconnect stays a direct generated API mutation in the current SPA, followed by a fresh bounded status read. Disable only the submitted action and announce `Connecting Bitbucket` or `Reconnecting Bitbucket` in the existing polite live region.
- A connection or capability mutation failure preserves the previous visible profile and uses the existing error region. Never expose a provider response, raw scope, token, client secret, workspace, or connection generation.
- Phase 3 performs zero provider writes. Capability readiness is not an affordance for branch, commit, or pull-request actions.

### Published mapping imports

- Each published mapping row shows repository side(s), exact configured branch(es), one status Badge, the last successful baseline, the latest execution timestamp, retry count when greater than zero, and one operational action.
- For a direct mapping, show one baseline commit. For a separate mapping, show `Keys` and `Translations` commits together; never present one side as current while the other is pending or unreconciled.
- A missing baseline renders `No successful import yet`; it is not an absent or blank table cell.
- Action labels follow this exact state table:

| Condition | Action label | Behavior |
|-----------|--------------|----------|
| No logical import | `Run import` | Create the durable logical import and start its first execution. |
| Current baseline | `Refresh import` | Resolve the branch again and execute once. |
| Failed execution | `Retry import` | Reuse the same logical import record and start its next execution. |
| Queued/running | `Import in progress` | Disabled, `aria-busy="true"`; no cancel action. |
| Rewrite detected | `Review baseline change` | Open the mapping-scoped reconciliation dialog; do not start another execution. |

- Do not add `Import all`, scheduled refresh, automatic retry, retry countdown, or a cancel button.
- `Run import`, `Refresh import`, and `Retry import` make one generated mutation request. Prevent duplicate submission with both state and ref guards; no optimistic status or baseline change is allowed.
- On accepted execution, refetch the server projection and poll status every 2 seconds through 30 seconds, then every 5 seconds through 90 seconds. Polling observes the one durable execution; it does not retry provider work.
- Stop automatic polling at 90 seconds and show `Automatic status updates paused` plus `Refresh status`. Leaving the page does not cancel the worker job.
- Announce only status transitions in one mapping-list `aria-live="polite"` region. Unchanged polls must not repeat announcements or move focus.
- A manual retry replaces the visible current error/status for the same logical import, retains and increments `Retry {count}`, and updates `Latest execution`. Never render a timeline, attempt selector, or prior-error history.
- When a failed refresh retains a baseline, keep that baseline fully visible and label the mapping `May be stale`. When a first import fails, show `Import failed` and `No successful import yet`.

### Error and recovery behavior

- Execution errors render beneath the owning row/article details, not as a page banner, toast, modal, or global administration alert.
- An error region contains category heading, one approved message, and no button or navigation link. The normal row action remains the only retry control.
- Use these exact category headings and copy:

| Category | Heading | Message |
|----------|---------|---------|
| Connection/authentication | `Bitbucket connection required` | `The organizational Bitbucket connection is not ready for imports. An administrator must reconnect it before retrying this mapping.` |
| Permission | `Repository access denied` | `Bitbucket denied access to this repository or branch. Review the organizational connection and repository permissions, then retry from this mapping.` |
| Rate limit | `Bitbucket request limit reached` | `Bitbucket is temporarily limiting requests. Wait a few minutes, then retry this import from the mapping.` |
| Missing repository, branch, or file | `Import source not found` | `The configured repository, branch, or localization file could not be found. Review the mapping configuration before retrying.` |
| Timeout | `Import timed out` | `Bitbucket did not respond within the safe time limit. The last successful baseline is unchanged. Retry later.` |
| Provider unavailable | `Bitbucket unavailable` | `Bitbucket could not complete this import. The last successful baseline is unchanged. Retry later.` |
| Bounded import failure | `Import did not complete` | `The source could not be read within the safe import limits. The last successful baseline is unchanged. Review the mapping before retrying.` |

- When no last baseline exists, replace the sentence `The last successful baseline is unchanged.` with `No import baseline was created.`
- Do not interpolate provider messages, status text, source body content, credentials, unsafe URLs, or stack traces. A stable server error code may select copy but must not be rendered as prose.
- Page-load failure replaces only the Phase 3 content region with the existing `We could not load this page. Retry without leaving the administration area.` and `Retry loading page` action.

### Rewritten-baseline reconciliation

- `Review baseline change` opens only from the standard mapping action cell/card. It is not embedded in an error Alert.
- Dialog title: `Review rewritten source history`.
- Introductory copy: `This branch no longer descends from the last successful baseline. Review the complete localization-file change before choosing a new baseline.`
- While details load, render stable Skeleton geometry and `Loading baseline comparison`. If the proposed baseline or complete file delta cannot be read, render `Baseline comparison unavailable` with `The proposed source could not be read safely. Close this review and retry the import later.`; omit the confirm action.
- Show repository-side blocks in `Keys`, then `Translations` order for separate mappings and one `Source` block for direct mappings. Each block contains repository, exact opaque branch, `Current baseline`, and `Proposed baseline`.
- Commit values are monospace and copyable in full. Do not link to provider URLs or infer ancestry client-side.
- Show summary counts in this order: `Added`, `Modified`, `Removed`. File rows contain `Change`, `Repository side`, and `File path`; each change uses text plus Badge, never color alone.
- A zero-delta rewrite renders `No localization file changes detected` and still requires confirmation because commit ancestry changed.
- If the backend marks the delta incomplete, truncated, stale, or over budget, show a blocking error and omit the confirm action. Never confirm from a partial list.
- For separate mappings, both repository sides are reviewed and confirmed in one dialog and one mutation. There is no per-side confirmation or partial success state.
- Confirmation title: `Use the rewritten baseline?`.
- Confirmation body: `The proposed commits will replace the current baseline for this mapping. Pending edits remain tied to the old baseline and cannot be submitted until they are reapplied or reconciled.`
- Actions are `Keep current baseline` and `Confirm new baseline`. The confirm action uses Accent, not Destructive, because it accepts a verified source identity rather than deleting data.
- While confirming, disable both actions, set `aria-busy` on `Confirm new baseline`, and prevent outside-click/Escape closure. Only a fresh backend-confirmed mapping projection changes the baseline and status.
- A stale proposal or concurrent mapping change keeps the dialog open, focuses `Baseline changed again`, and says `The proposed baseline is no longer current. Close this review and run the import again.`

### Product-level freshness summary

- When `affected_mapping_count` is zero, render no freshness warning and do not invent an `All current` success banner.
- When the count is one, render warning Badge `1 mapping may be stale`.
- When greater than one, render warning Badge `{count} mappings may be stale`.
- Supporting copy: `A recent import failed, so the last successful baseline remains active.`
- The summary has no action or link. Administrators use the existing Mappings navigation themselves.
- The count is server-owned and scoped to this product. The UI never derives it by counting the currently loaded or paginated mapping rows.

### Existing destructive connection action

- Keep the existing named confirmation for `Revoke connection`.
- Title: `Revoke the Bitbucket connection?`
- Body: `New imports, branch reads, previews, confirmations, and publications will be blocked until an administrator reconnects. Existing successful baselines remain recorded.`
- Confirm label: `Revoke connection`.
- Revocation remains non-optimistic and Destructive red. It does not delete successful baselines or import records.

### Open-axis considerations

- Network loss uses the fixed connection/provider error path; there is no offline queue or optimistic baseline.
- Import observation is polling-based. No WebSocket, invented percentage, optimistic completion, or real-time collaboration UI is introduced.
- Respect `prefers-reduced-motion`; status, Skeleton, dialog, and focus behavior remain complete without animation.
- English-only copy, RTL mirroring, print layouts, voice, and gesture-specific interaction remain outside this phase, while normal reflow and accessible names remain required.

## Accessibility Contract

- Maintain one `h1` per route and hierarchical `h2` section headings. The rewritten-history dialog has an associated title and description.
- Status labels remain understandable without color. The affected count, file-change kind, capability readiness, and import state all have text.
- The mapping status region announces only state transitions. Polling must not announce unchanged states, move focus, or reset the user's scroll position.
- On row mutation failure, focus the owning error Alert only when the failure follows a user action; background polling failures announce politely without stealing focus.
- On dialog load/confirmation error, focus the error Alert. On cancel or successful close, restore focus to `Review baseline change`.
- The dialog traps focus while open. During confirmation, outside click and Escape cannot abandon an uncertain mutation.
- Tables have semantic headers and an accessible name. Mobile articles preserve the exact label/value/action order.
- Local overflow regions are keyboard-focusable and have an accessible label. The page itself never scrolls horizontally at `320px` or 200% zoom.
- Any icon-only copy control has `aria-label="Copy full commit"`, a Tooltip, visible focus, and an announced result `Full commit copied`; the copied hash is never announced automatically.
- Touch targets are at least `44px × 44px` on mobile/coarse pointer. Primary, retry, reconciliation, and destructive actions retain visible text and never depend on hover.
- Do not use focus or live-region behavior to expose raw provider diagnostics or full hashes unless the user explicitly invokes copy.
